# Git 知识点 01：提交与推送

> 适用仓库：mini-mall。Git 根目录是 `mini-mall/`，代码在子目录 `v1/`，远端为 `https://github.com/3314117689/mini-mall.git`。
> 学习目标：改完代码后，能把改动正确地提交到本地、推送到 GitHub，并确认远端真的更新了。

## 0. 一句话结论

```bash
git add <文件>          # 挑出这次要提交的改动
git commit -m "说明"    # 存成一次本地快照
git push origin main    # 把本地快照同步到 GitHub
```

`commit` 只写本地，`push` 才上 GitHub。只 commit 不 push，GitHub 上什么都看不到。

## 1. 三个动作对应三个区域

| 区域 | 含义 | 对应动作 |
|---|---|---|
| 工作区 | 你正在编辑的文件 | 改代码 |
| 暂存区 | 这次准备提交的改动 | `git add` |
| 本地仓库 | 本机的历史快照 | `git commit` |
| 远程仓库 | GitHub 上的副本 | `git push` |

提交不是"保存文件"，而是"给当前代码拍一张照片，存进历史"。照片只存在本地，推送后才同步到远端。

## 2. 标准提交流程（五步）

```bash
# 1. 看现在有什么改动
git status

# 2. 看具体改了什么（提交前必须看一眼，防止把调试代码带进去）
git diff

# 3. 把要提交的文件放进暂存区
git add v1/mall-order/src/main/java/com/mall/order/service/impl/OrderServiceImpl.java

# 4. 提交到本地仓库
git commit -m "feat: 任务单#04 订单服务基础五件套"

# 5. 推送到 GitHub
git push origin main
```

推送后再验证一次：

```bash
git status -sb      # 不应再出现 ahead 字样
git log --oneline -3
```

`git status -sb` 第一行如果显示 `## main...origin/main`，说明本地和远端一致；显示 `[ahead 1]` 说明还有提交没推上去。

## 3. 提交信息规范（本项目约定）

格式：`类型: 说明`，中文，说明写"做了什么"而不是"改了代码"。

| 类型 | 用途 | 示例 |
|---|---|---|
| `feat` | 新功能 | `feat: 任务单#04 用户服务增删改` |
| `fix` | 修 bug | `fix: 修正订单服务名误写为 product-service` |
| `docs` | 文档 | `docs: 更新 DEV_LOG 与规划对照表` |
| `chore` | 杂项 | `chore: 忽略 IDEA 元数据` |

反例：

- `update`
- `修改`
- `提交代码`
- `完成了很多功能`

好提交信息的标准：只看标题就知道这次改了什么，不需要点进 diff。

## 4. 只提交一部分，或提交错了怎么办

### 只提交部分文件

```bash
git add v1/mall-user/          # 只暂存用户模块
git commit -m "feat: 用户服务增删改"
```

### 看清暂存区里到底有什么

```bash
git diff --staged
```

### 把文件从暂存区拿出来（撤销 add，不改代码）

```bash
git restore --staged v1/mall-user/src/main/java/com/mall/user/entity/User.java
```

### 撤销工作区的改动（危险，代码会丢）

```bash
git restore v1/mall-user/src/main/java/com/mall/user/entity/User.java
```

### 改最近一次提交的说明（还没推送时）

```bash
git commit --amend -m "新的提交说明"
```

已经 push 过的提交不要 amend，否则本地和远端历史不一致，推送会被拒。

## 5. 推送到 GitHub

### 第一次推送

```bash
git remote -v                  # 确认远端地址
git push -u origin main        # -u 记住跟踪关系，以后不用再写 origin main
```

### 之后推送

```bash
git push
```

### 推送失败：`rejected (non-fast-forward)`

原因：远端有你本地没有的提交（比如在 GitHub 网页上改过文件，或另一台电脑推送过）。

```bash
git pull --rebase origin main   # 先把远端提交拉到本地并排在前面
git push
```

不要用 `git push -f` 解决，会覆盖远端历史。

## 6. .gitignore 的作用

仓库根目录的 `.gitignore` 决定哪些文件**永远不进入 Git**，例如：

```text
target/      # Maven 编译产物
.idea/       # IDEA 配置
*.iml
logs/        # 运行日志
```

规则：

- 被忽略的文件在 `git status` 里看不到，`git add .` 也不会加进去
- 如果某个文件已经被提交过，后来才加进 .gitignore，它仍会被跟踪，需要先移出版本库：

```bash
git rm -r --cached target
git commit -m "chore: 停止跟踪编译产物"
```

## 7. 本项目专属注意

1. **在 `mini-mall/` 根目录执行 Git 命令**，`v1/` 只是仓库里的子目录。
2. **多模块一起提交**：改了 common 又改了 user 时，两边一起提交，否则单独检出某个提交会编译失败。
3. **代理只配在仓库级**：`git config http.proxy http://127.0.0.1:7891`，换仓库不受影响。
4. **`warning: LF will be replaced by CRLF` 不是错误**：Windows 换行符提示，可以忽略。
5. **提交前不要带 `target/`、`.idea/`、数据库密码**；目前各服务 `application.yml` 里是明文密码，公开仓库要注意。

## 8. 常见坑

| 现象 | 原因 | 处理 |
|---|---|---|
| `nothing to commit, working tree clean` | 文件没保存、改动已提交、或被 .gitignore 忽略 | 先保存文件，再 `git status` 确认；被忽略的用 `git check-ignore -v <文件>` 查规则 |
| `push` 被拒（non-fast-forward） | 远端有本地没有的提交 | `git pull --rebase origin main` 后再 push |
| 提交里混进了无关文件 | 用了 `git add -A` 没检查 | 提交前 `git status` + `git diff --staged` |
| 提交信息看不懂 | 写成了"修改""更新" | 按第 3 节格式重写 |
| GitHub 上看不到新代码 | 只 commit 没 push | `git status -sb` 看是否 ahead，然后 push |

## 10. 命令速查

| 目的 | 命令 |
|---|---|
| 看状态 | `git status` / `git status -sb` |
| 看未暂存改动 | `git diff` |
| 看已暂存改动 | `git diff --staged` |
| 暂存指定文件 | `git add <路径>` |
| 暂存全部改动 | `git add -A` |
| 取消暂存 | `git restore --staged <路径>` |
| 提交 | `git commit -m "feat: 说明"` |
| 修改最近一次提交说明 | `git commit --amend -m "新说明"` |
| 查看最近提交 | `git log --oneline -5` |
| 推送到远端 | `git push` / `git push -u origin main` |
| 拉远端并变基 | `git pull --rebase origin main` |
| 查文件被哪条规则忽略 | `git check-ignore -v <文件>` |
