# 00 讲解规则（写文档、讲代码都按这个来）

> 规则源头在仓库根目录 `AI_CONTEXT.md` 的铁律 4 / 10 / 11 / 12。这里是落地版，写日志和讲解时直接照做。

## 一句话目标

让你读文档时**只顺着数据往下走**，不需要回忆上下文、不需要猜数据、不需要二次翻译。

## 六条硬规则

1. **一条命令为轴**
   写清 `方法 + 路径 + 参数真实值`。例：`GET /product/2`，不要写"查询商品接口"。

2. **分岔先行**
   先把"这条命令有几种结局、分岔点在哪一行、由哪个值决定"列成表，再逐个结局走。禁止讲到一半才出现新的可能。

3. **数据编号，全程跟踪**
   给每条被跟踪的数据编号 `[D1]`~`[Dn]`。每步写 `当前值 · 来源 · 去向`。
   数据变形（`String → Long`、`Product → JSON`）必须交代"是不是同一条数据；不是，从哪来"。

4. **调用关系不能断**
   文档开头放调用链表（谁、哪一行、干了什么）。每次"返回/交回"都要写明：回到哪个类的哪一行、返回值给谁用。

5. **禁止省略式描述**
   不许写"有值/没值/处理一下就返回了"。必须写是哪个变量、值具体是什么（`null` / 哪段 JSON / `NullValue` 标记）。

6. **真实类名 + 归属，禁止外号**
   统一用真实类名，标"本项目 / 哪个框架"。禁用"门卫""本尊"这类代称。
   类或方法第一次出现给 `文件路径 + 行号 + 代码原文`；方法名永远带类名（`ProductServiceImpl.getById`）。

## 框架怎么讲

- 只讲**动作级**：它替你做了哪几步、这些步骤让数据变成了什么。
- **只有影响数据走向的框架环节才点类名**（如 `CacheInterceptor` 决定查/写 Redis）。
- 不贴框架源码、不展开类层级；对数据无影响的内部细节（注解解析器、消息转换器内部）一笔带过。
- 判断标准：读者不知道这个类名，会不会看不懂数据走向？不会，就略过。

## 可复用的部分

同一规则在不同分支重复出现时，写"同分支①第 X 步"，不重复展开。

## 每篇的收尾

1. **断点验证**：在哪停、看什么变量、看到什么值能证明走了这条路。
2. **自测题**：3 道，不附答案。
