# 02 L0 地基 + L1 异常框架

> 按铁律 11：总览表只做导航，过程在"逐步行进"里。
> 注意：L0/L1 时 `ProductServiceImpl.getById` 第 30 行是 `productMapper.selectById(id)`；L5 之后改成先查缓存（见 06 章）。本章按 L0 当时的形态讲，涉及当前代码时注明差异。

## 一、L0：`GET /product/1` 的调用链

**命令入场**：`GET http://localhost:8082/product/1`

| 顺序 | 谁 | 在哪 | 干了什么 |
|---|---|---|---|
| 1 | Tomcat 线程 | — | 按路径找到 `ProductController.getById` |
| 2 | `ProductController.getById` | 第 25-26 行 | 接收 `id`，调 `productService.getById(id)` |
| 3 | `ProductServiceImpl.getById` | 第 28-30 行 | 打"查询商品"日志，调 Mapper |
| 4 | `ProductMapper.selectById` | 第 20-21 行 | 注解 SQL，由 MyBatis 执行 |
| 5 | MySQL | — | 返回一行或 0 行 |
| 6 | `Result.ok` | 第 25-31 行 | 包装成统一返回体 |
| 7 | 框架（Spring MVC） | — | 转 JSON 写回浏览器 |

**数据编号**

| 编号 | 数据 | 初始值 | 谁产生 |
|---|---|---|---|
| `[D1]` | 商品 id | `"1"` → `1L` | 浏览器 URL，框架转 Long |
| `[D2]` | 商品对象 | `Product{id=1,...}` 或 `null` | MyBatis |
| `[D3]` | 返回体 | `Result{code,msg,data}` | `Result.ok` |
| `[D4]` | 响应文本 | JSON 字符串 | 框架序列化 |

## 二、L0 结局①逐步行进：商品存在

### 第 1 步｜请求到达

```java
// 文件：mall-product/src/main/java/com/mall/product/controller/ProductController.java
// 行号：24-26
@GetMapping("/{id}")
public Result<Product> getById(@PathVariable Long id) {
    return Result.ok(productService.getById(id));
}
```

- 【你写的】第 24 行声明路径；第 25 行 `@PathVariable Long id` 表示从 URL 路径取值。
- 【注解】`@GetMapping` 让框架能按路径找到方法；`@PathVariable` 指定值来自路径而不是请求体。
- 【框架动作】Tomcat 派线程；按路径匹配方法；把 URL 里的 `1` 转成 `Long` 塞进参数。
- 【数据】`[D1]` `"1"` → `1L` · 来源：URL · 去向：`getById` 的参数 `id`。

### 第 2 步｜算括号里的

- 【你写的】第 26 行从里往外执行：先 `productService.getById(1L)`。
- 【数据】`[D1] = 1L` · 去向：`ProductServiceImpl.getById` 的参数；`[D3]` 尚未产生。

### 第 3 步｜进入 `ProductServiceImpl`

```java
// 文件：mall-product/src/main/java/com/mall/product/service/impl/ProductServiceImpl.java
// 行号：27-30（L0 版本）
@Override
public Product getById(Long id) {
    log.info("查询商品, id={}", id);
    Product product = productMapper.selectById(id);
```

- 【你写的】第 29 行打印"查询商品, id=1"；第 30 行调 Mapper 并把返回值装进 `product`。
- 【数据】`[D1] = 1L` · 从 Controller 传入 · `[D2]` 还不存在。

### 第 4 步｜进 Mapper 执行 SQL

```java
// 文件：mall-product/src/main/java/com/mall/product/mapper/ProductMapper.java
// 行号：20-21
@Select("select id, name, price, stock, create_time from product where id = #{id}")
Product selectById(Long id);
```

- 【你写的】Mapper 是接口，方法上挂 SQL。
- 【注解】`@Select` 把 SQL 绑在方法上；`#{id}` 是预编译占位符，不是字符串拼接。
- 【框架动作】MyBatis 给接口造代理；把 `#{id}` 换成 `1`；连 MySQL 执行。
- 【数据】`1L` · 作为参数传进 `selectById(1)` → SQL 的 `?` 填 `1`。

### 第 5 步｜结果集映射成对象

- 【框架动作】MyBatis 按 `map-underscore-to-camel-case: true`（`application.yml`）把 `create_time` 映射成 `createTime`，造出 `Product`。
- 【数据】MySQL 一行 → `[D2] = Product{id=1, name="测试商品", price=9.90, stock=100}` · 作为 `selectById(1)` 返回值回到第 30 行。

### 第 6 步｜返回

- 【你写的】L0 版本没有判空，第 30 行取到后直接 `return product`。
- 【数据】`[D2] Product` · 变成 `ProductServiceImpl.getById` 的返回值 · 交给 Controller 第 26 行。

### 第 7 步｜包装 `Result`

```java
// 文件：mall-common/src/main/java/com/mall/common/result/Result.java
// 行号：25-31
public static <T> Result<T> ok(T data) { ... }
```

- 【你写的】`Result.ok([D2])` → `code=0`、`msg="ok"`、`data=[D2]`。
- 【数据】`[D2]` → `[D3] = Result{code=0, msg="ok", data=Product{...}}` · 成为 Controller 返回值。

### 第 8 步｜序列化

- 【框架动作】Spring MVC（框架）把 `[D3]` 转成 JSON 写进响应体。
- 【数据】`[D3]` → `[D4] = {"code":0,"data":{"id":1,...},"msg":"ok"}` · 去向：浏览器。

> L1 补上的差异：现在第 32 行有 `if (product == null) throw`，所以"查不到"不再是返回 `data=null` 的成功响应。

## 三、L0：`@Autowired` 注入的心智模型（已确认）

1. 注入了就**只管用**，其余全是框架做的。
2. 字段只声明不赋值就是 `null`，没注入就调 = 空指针。
3. 接口（如 `ProductMapper`）源码里没有实现类，`new` 不出来，**只能靠框架注入**。
4. 两个时刻：**启动期**框架执行"字段 = 容器里的对象"（源码里看不到）；**请求期**你只写调用语句。
5. 每层只注入下一层：Controller → Service → Mapper。
6. 调接口方法 = 直接执行实现类的方法体，中间没有"先执行接口"。
7. `return Result.ok(productService.getById(id))` 从里往外执行。

## 四、L1：异常四件套的调用链

**默写顺序（依赖顺序）**：`Result` → `ErrorCode` → `BizException` → `GlobalExceptionHandler` → Service 里 `throw`

| 名字 | 文件 | 作用 |
|---|---|---|
| `Result` | `mall-common/.../result/Result.java` | 统一返回体：`code/msg/data` |
| `ErrorCode` | `mall-common/.../exception/ErrorCode.java` | 错误码枚举（1002 商品不存在等） |
| `BizException` | `mall-common/.../exception/BizException.java` | 业务异常，带 `code` |
| `GlobalExceptionHandler` | `mall-common/.../exception/GlobalExceptionHandler.java` | 接住异常转 `Result` |

## 五、L1 结局②逐步行进：商品不存在

**入场**：`GET /product/999`，MySQL 没有 999。

第 1~5 步同 L0 结局①，只是 `[D1] = 999L`、SQL `Total: 0`。

### 第 5 步的结果｜`[D2] = null`

- 【框架动作】MyBatis 没有对象可造，返回 `null`。
- 【数据】`[D2] = null`（来自"查不到"）。

### 第 6 步｜判空成立

```java
// 文件：mall-product/.../service/impl/ProductServiceImpl.java
// 行号：32-36
if (product == null) {
    log.warn("商品不存在, id={}", id);
    throw new BizException(ErrorCode.PRODUCT_NOT_FOUND);
}
return product;
```

- 【你写的】第 32 行条件 true → 第 33 行打 warn → 第 34 行抛异常。
- 【数据】`[D2] = null` → 使用 `ErrorCode.PRODUCT_NOT_FOUND`（`code=1002`、`msg="商品不存在"`）。

### 第 7 步｜枚举被拆进异常对象

```java
// 文件：mall-common/src/main/java/com/mall/common/exception/BizException.java
// 行号：18-21
public BizException(ErrorCode errorCode) {
    super(errorCode.getMsg());
    this.code = errorCode.getCode();
}
```

- 【你写的】把枚举的 `msg` 存成异常的 message，`code` 存成字段。
- 【数据】`ErrorCode(1002,"商品不存在")` → `BizException{code=1002, message="商品不存在"}`。

### 第 8 步｜异常开始飞

- 【你写的】第 34 行 `throw` 之后，第 36 行 `return` 不执行；Controller 第 26 行 `Result.ok(...)` 也不执行。
- 【数据】`BizException` 沿调用链往回飞：`ProductServiceImpl.getById` → `ProductController.getById` → 框架。

### 第 9 步｜全局处理器接住

```java
// 文件：mall-common/src/main/java/com/mall/common/exception/GlobalExceptionHandler.java
// 行号：25-29
@ExceptionHandler(BizException.class)
public Result<Void> handleBizException(BizException e) {
    log.warn("业务异常: code={}, msg={}", e.getCode(), e.getMessage());
    return Result.fail(e.getCode(), e.getMessage());
}
```

- 【注解】`@ExceptionHandler(BizException.class)` 声明"这类异常归我接"。
- 【框架动作】框架把飞行中的异常作为参数 `e` 交给这个方法。
- 【数据】`BizException{code=1002,...}` → `[D3] = Result{code=1002, msg="商品不存在", data=null}`。

### 第 10 步｜序列化

- 【框架动作】框架把 `[D3]` 转 JSON；HTTP 状态仍是 200（全工程约定）。
- 【数据】`[D4] = {"code":1002,"data":null,"msg":"商品不存在"}`。

## 六、三个面试速答

- **为什么继承 `RuntimeException`**：受检异常会污染所有方法签名，业务层本来也不打算就地处理。
- **为什么 HTTP 仍返回 200**：前端只看 body 里的 `code`，统一约定。
- **为什么 warn 和 error 分开**：业务失败是预期内（warn，不带堆栈）；兜底是意外故障（error，带堆栈）。
