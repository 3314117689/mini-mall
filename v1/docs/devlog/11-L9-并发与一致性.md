# 11 L9 并发与一致性

> 按铁律 11 写：总览表只做导航，过程在"逐步行进"里。
> 本章的一条轴：**一条下单命令 `POST /api/order/create`，从"串行两次 Feign + 直接 insert"改到"线程池内并行编排 + 超时降级 + 号段订单号 + Redis Lua 扣库存"。**
> 环境事实：MySQL **5.7.32**、Redis **5.0.5**、Boot **4.1.2** + JDK **17**；网关 order/product 路由限流 **2/秒、桶 5**，所以并发压测一律**直连业务端口并带三个 `X-Mall-*` 头**。

## 一、这一层解决什么

L2~L8 的下单只有一条路：`OrderServiceImpl.create` 先 `getUser`、再 `getProduct`、最后 `insert`。数据量小的时候看不出问题，并发上来后暴露四件事：

1. **串行调用**：用户和商品两件事没有依赖，却一前一后等；
2. **超时不可控**：只靠 Feign 的 3 秒读超时，慢依赖会一直占着 Tomcat 线程；
3. **库存不扣**：并发下单会超卖，`product.stock` 没人保证不被扣成负数；
4. **订单号用自增主键**：对外暴露业务量，分库分表后不可用。

L9 不加新框架，只加 **JDK 并发工具 + Redis**，把四件事逐个量化。

## 二、技术点清单

| # | 技术点 | 落点 | 一句话作用 | 面试频度 |
|---|---|---|---|---|
| 1 | 线程池分级 | mall-order 两个池 | 在线请求池（有界队列 + AbortPolicy，宁可快失败）与补偿池（CallerRunsPolicy，不能丢）隔离 | ★★★ |
| 2 | 反压与拒绝兜底 | 自定义拒绝处理器 + `create` | 队列满记录 `active/queue/poolSize` 后抛 `RejectedExecutionException`，业务返回 4291 | ★★★ |
| 3 | `CompletableFuture` 编排 | `OrderServiceImpl.create` | 用户/商品并行取，`thenCombine` 合并 | ★★★ |
| 4 | `orTimeout` 超时降级 | 同上 | 等待方 2 秒未齐就放弃；它**不取消**底层任务，只影响等待结果 | ★★★ |
| 5 | 异步线程 ThreadLocal 传递 | 同上 | L7 的 `FeignAuthInterceptor` 依赖 `UserContext`；换线程必须"进任务 set、finally clear" | ★★★ |
| 6 | 号段发号器 | mall-order | Redis `INCRBY step` 取一段 + 本地 `AtomicLong` 发号 + CAS 换段 | ★★★ |
| 7 | Redis Lua 原子扣减 | mall-product | "判断 + 扣减"在一次 Lua 里原子执行，避免 GET 后 DECR 的竞态 | ★★★ |
| 8 | DB 条件扣减兜底 | mall-product | `update ... set stock=stock-n where id=? and stock>=n`，0 行即失败；Redis 挂了也不超卖 | ★★★ |
| 9 | 失败补偿 | `OrderServiceImpl.create` | 扣库存成功但订单落库失败 → 调 release 回补；补偿走补偿池 | ★★ |
| 10 | 一致性已知缺口 | 本文档 | 扣减成功但响应超时 → 库存减了、订单没落；无分布式事务，只能对账 | ★★ |

### 结局①逐步行进：池内执行成功

#### 第 1 步｜Tomcat 线程进入 `create`

- 【你写的】参数校验后打日志 `下单, userId=1, productId=1, num=1`。
- 【数据】`[D1]=1`、`[D2]=1/1`；此时日志线程是 `nio-8083-exec-1`。

#### 第 2 步｜取身份快照并提交任务

```java
// 文件：mall-order/src/main/java/com/mall/order/service/impl/OrderServiceImpl.java
// 行号：89-103
LoginUser loginUser = UserContext.get();
Future<RemoteSnapshot> future;
try {
    future = remoteExecutor.submit(() -> {
        log.info("远程调用任务开始, thread={}, userId={}",
                Thread.currentThread().getName(), userId);
        UserContext.set(loginUser);
        try {
            UserDTO user = remoteService.getUser(userId);
            ProductDTO product = remoteService.getProduct(dto.getProductId());
            return new RemoteSnapshot(user, product);
        } finally {
            UserContext.clear();
        }
    });
} catch (RejectedExecutionException e) {
    log.warn("线程池拒绝下单任务, userId={}, productId={}", userId, dto.getProductId());
    throw new BizException(ErrorCode.POOL_BUSY);
}
```

- 【你写的】`loginUser` 是**当前请求线程**读出来的快照；worker 线程的 ThreadLocal 默认是空的，所以必须 `set`。
- 【注解】`@Qualifier(ThreadPoolConfig.REMOTE_EXECUTOR)` 决定注入哪个池（两个同类型 Bean 靠名字区分）。
- 【框架动作】`ThreadPoolTaskExecutor.submit` 把任务放进队列，由空闲线程取走执行。
- 【数据】`[D3]` 被复制进任务闭包；`[D5]=mall-remote-1`。

#### 第 3 步｜worker 里发两次 Feign

- 【你写的】`remoteService.getUser(userId)` 和 `remoteService.getProduct(productId)`。
- 【框架动作】`FeignAuthInterceptor.apply` 从 worker 线程的 `UserContext` 取三个头写进请求；下游 `GatewayAuthInterceptor` 读头重建用户。
- 【数据】`[D4]`：`UserDTO.id=1`、`ProductDTO.price=9.90`。
- 反证：如果忘了 `UserContext.set`，`FeignAuthInterceptor` 拿不到用户，不会写头，下游返回 `4010`。

#### 第 4 步｜Tomcat 线程等待并落库

- 【你写的】`future.get()` 阻塞到任务结束；然后 `orderMapper.insert(order)`。
- 【数据】`[D6]=100011`（L8 数据之后的自增值）。
- 注意：这一步 **Tomcat 线程仍在阻塞等待**，只是"等待的地点"从两次 Feign 之间挪到了 `future.get()`；真正的并行和超时在 L9-2。

### L9-1 坑

1. **无界队列等于没有反压**：`LinkedBlockingQueue` 不传容量就是 `Integer.MAX_VALUE`，任务全堆在内存里，响应时间无限拉长；必须用有界队列。
2. **`TaskRejectedException` 是 `RejectedExecutionException` 的子类**：Spring 的 `ThreadPoolTaskExecutor` 抛的是前者，`catch (RejectedExecutionException)` 能接住，别再单独 catch 子类。
3. **换线程就丢 ThreadLocal**：不 `set` 身份，Feign 不带 `X-Mall-*`，下游直接 `4010`；不 `clear`，线程复用会串号。
4. **本步只搬走了阻塞点**：Tomcat 线程还是在 `future.get()` 上等，串行也还在；L9-2 才做并行和超时。
5. **池参数用 `@Value` 默认值 + 启动参数覆盖**：验收时不用改 yml，重启参数即恢复，避免把测试值提交进仓库。
6. **冷启动会放大耗时**：商品服务首次查询要初始化连接池，叠加 2 秒 sleep 会超过 Feign 3 秒读超时，出现一次 `2003`；预热一次再压测可避免。

### L9-2 坑

1. **`orTimeout` 不取消底层任务**：到点只是让等待方拿到 `TimeoutException`；底层 Feign 调用还在跑，可能继续打日志。本例两个调用都是只读，所以没有副作用；如果底层是扣库存，必须自己处理"超时但实际成功"。
2. **两层超时会竞速**：`orTimeout(2s)` 与 Feign 读超时（3s）/连接超时（3s）谁先到就返回谁。停 product 时如果连接失败慢于 2s，会先得到 `2004` 而不是 `2003`；验收时用 `connect-timeout=500ms` 才能稳定看到 `2003`。
3. **HTTP 长连接会复用旧连接**：停掉下游后，连接池里的旧连接可能先等到读超时而不是立刻连接拒绝，这是 `2002` 测试必须同时调小读超时的原因。
4. **异常要层层剥**：`CompletableFuture.get()` 外层是 `ExecutionException`，里面可能还有 `CompletionException`；`unwrap` 剥到真正的 `BizException/TimeoutException` 再分诊。
5. **冷启动会误判超时**：第一次请求要初始化下游连接池 + 负载均衡，2 秒上限可能不够；压测前先各打一次 `/user/1`、`/product/1` 预热。
6. **两个任务都要带身份**：`withUserContext` 必须包住两个 `supplyAsync`，只包一个会导致另一个请求丢 `X-Mall-*`。

| `[D2]` | 库存 key | `mall:stock:1` | `KEY_PREFIX + productId` |
| `[D3]` | Lua 返回值 | `99`（成功）/ `-1`（不足）/ `-2`（key 丢失） | Lua |
| `[D4]` | DB 更新行数 | `1`（成功）/ `0`（失败） | MySQL |
| `[D5]` | DB stock | `100 → 99` | MySQL |
| `[D6]` | Redis stock | `100 → 99` | Redis |
| `[D7]` | 商品缓存 | `product::1` 被删 | `CacheManager` |

**四个结局**

| 结局 | 分岔点 | 条件 | 结果 |
|---|---|---|---|
| ① 扣减成功 | Lua 返回 `>=0` 且 DB 更新 1 行 | 库存足够 | `code=0`，返回剩余库存 |
| ② 库存不足 | Lua 返回 `-1` | Redis 库存 < num | `code=1006`，DB/Redis 都不变 |
| ③ Redis 与 DB 不一致 | DB 更新 0 行 | Redis 认为够、DB 不够 | Redis 回补 num，返回 `1006`（规则推演） |
| ④ Redis 不可用 | `hasKey/execute` 抛异常 | 连接失败 | 跳过 Redis，直接 DB 条件扣减，仍返回成功 |

### 结局①逐步行进：扣减成功

#### 第 1 步｜加载库存 key

- 【数据】首次扣减时 `mall:stock:1` 不存在，`ensureStockLoaded` 从 DB 读 `stock=100`，`setIfAbsent` 写入。
- 【你写的】只用 `setIfAbsent`，不直接 `set`：避免覆盖并发扣减后已经变小的值。

#### 第 2 步｜Lua 原子扣减

```lua
local stock = redis.call('get', KEYS[1])      -- "100"
if not stock then return -2 end
local num = tonumber(ARGV[1])                 -- 1
stock = tonumber(stock)                       -- 100
if stock < num then return -1 end
redis.call('decrby', KEYS[1], num)            -- 99
return stock - num                            -- 99
```

- 【框架动作】Redis 单线程执行整段脚本，"读 100 → 判断 → 减 1" 之间不会插入别的命令，所以两个并发请求不可能都读到 100。
- 【数据】`[D3]=99`、`[D6]=99`。

#### 第 3 步｜DB 条件扣减

```sql
update product set stock = stock - 1 where id = 1 and stock >= 1;
```

- 【数据】`[D4]=1`、`[D5]=99`。
- 【你写的】`and stock >= 1` 是关键：没有它，并发下 DB 也能扣成负数。

#### 第 4 步｜清缓存并返回

- 【数据】`[D7]`：`product::1` 被删；下一次 `GET /product/1` 回源 MySQL 看到 `stock=99`。
- 实测响应：`{"code":0,"data":99}`。

### 结局②逐步行进：库存不足

- 【数据】`productId=1&num=1000`：Lua 读到 99 < 1000，返回 `-1`，**不执行 DECRBY**。
- 【数据】第 5 步 DB 根本不执行；返回 `{"code":1006,"msg":"库存不足"}`，DB/Redis 仍为 99。

### 结局③逐步行进：Redis 与 DB 不一致（规则推演）

- 【数据】假设 Redis 里是 100、DB 里是 0：Lua 扣成 99，DB `where stock>=1` 更新 0 行。
- 【你写的】`luaResult >= 0` 时执行 `INCRBY key num` 把 Redis 加回 100，再查一次商品区分"不存在（1002）"和"库存不足（1006）"。
- 结论：DB 是真相源，Redis 只是前置闸门；两边不一致时以 DB 为准。

### 结局④逐步行进：Redis 不可用

```text
java -jar mall-product-1.0.0.jar --spring.data.redis.port=6390
```

- 【数据】`hasKey` 连接 6390 失败，抛异常 → `catch` 把 `luaResult` 置 `null` → 直接走 DB 条件扣减。
- 实测：`{"code":0,"data":99}`，耗时 `3.13s`（连接超时），DB `100 → 99`，6379 上的 `mall:stock:1` 仍不存在。
- 结论：Redis 挂了会变慢，但不会超卖；代价是每个请求都打 DB，而且缓存失效也会失败（`evictProductCache` 已 catch，不影响扣减结果）。

### L9-4 实测

| 场景 | 操作 | 结果 |
|---|---|---|
| 单次扣减 | `num=1`，库存 100 | `code=0 data=99`；DB `99`；Redis `99`；商品缓存已删 |
| 库存不足 | `num=1000` | `code=1006`；DB/Redis 仍 `99` |
| 200 并发各扣 1 | 库存 100 | `ok=100 / insufficient=100 / other=0`，耗时 `2843ms`；DB `0`、Redis `0` |
| Redis 不可用 | 端口改 6390 | `code=0 data=99`，耗时 `3.13s`；DB `99`；Redis key 不存在 |

### L9-4 坑

1. **不能"先 GET 再 DECR"**：两步之间会插入其他请求，两个请求都看到 1，最后扣成 -1；Lua 才是原子。
2. **Lua 必须判断 key 是否存在**：key 不存在时不能当成 0 直接扣，否则会返回 -2 由 Java 重新加载。
3. **DB 条件更新不能省**：Redis 会丢数据、会被清空；`where stock >= num` 才是最后防线。
4. **初始值只能 `setIfAbsent`**：并发加载时 `set` 会把已经扣小的值覆盖回 100。
5. **扣减成功必须清商品缓存**：否则 `GET /product/1` 还返回旧的 100；这里用手动 `CacheManager.evict` 并 catch，避免 Redis 故障把扣减结果带崩。
6. **缓存 key 和库存 key 是两套**：`product::1` 是 L5 商品对象缓存，`mall:stock:1` 是 L9 库存计数，别混用。
7. **不要在共享 Redis 上直接停服**：本机 6379 还有另一个项目的 `sys_*` key；验证"Redis 不可用"用**端口错配**，不要真停 Redis。
8. **降级会变慢**：Redis 连接失败要等超时（实测 3.13s），生产需要更短的连接超时或本地缓存。
